# 2026-10-27 九项体验/性能修复：方案与取舍

本文对应本轮用户提出的九个问题。目标不是“看起来改了”，而是每一项都能说清：
**症状 → 根因 → 方案 → 代码位置 → 验证方式 → 边界**。

> 所有改动均在 `C:\Users\YOUR_USER\paperdesk` 工作区，未提交 git；用户数据未迁移、未删除。

## 0. 总原则

1. **先保数据，再谈效果**：表格/参考文献/附录的改动都走“保护优先”，宁可少擦一块，不能把原 PDF 内容擦掉。
2. **不靠加机器/加并发掩盖问题**：优先减少重复解析、重复 IPC、重复重建视图，避免把性能问题转嫁给模型或用户机器。
3. **对照联动必须有防回声**：双向滚动不能形成 A→B→A 的循环；所有联动写入都带 origin 标记。
4. **旧产物兼容**：旧译文没有新字段时退回旧行为；旧库没有新列时自动迁移。
5. **每项都留可回归的测试**：纯逻辑进 `scripts/test-unit.ts`，Python 进 `python/tests/`，交互进 `scripts/e2e.cjs`。

## 1. 文库里论文多了以后切换页面越来越卡

### 症状
打开几十篇以后，切换页面/切文档明显变卡，越用越慢。

### 根因
- 文库每一行都单独调一次作者 IPC（`AuthorLine` 逐条查），条目越多，首屏并发 IPC 和 SQL 越多，主进程被大量小请求打断。
- 每次切视图都重新挂载阅读器（`viewMode` 变化触发 `ErrorBoundary resetKey`），页码、滚动位置、已渲染页全部重来。
- 连续滚动时后台还在为远处页面做回填/文本层，和当前页抢主线程。

### 方案
- **作者一次批量取**：`LibraryList.tsx` 改为 `window.api.authors.forItemsLocal(ids)`，主进程一次 SQL 取回全部可见条目作者；逐条 IPC 删除。
- **视图缓存不重建**：`App.tsx` 同时挂载 `CompareView` 与单栏 `PdfViewer`，用 CSS 隐藏非当前视图；`ErrorBoundary` 的 `resetKey` 只跟“附件/译文”变化，不再跟 `viewMode` 变化。这样原文↔对照切换是显示切换，不是重新解析 PDF。
- **页面内容隔离**：`.scrollpage` 加 `content-visibility: auto` + `contain-intrinsic-size`，屏幕外页面不参与布局/绘制。
- **用户滚动时暂停回填**：`PdfViewer` 记录 `lastScrollAtRef`；滚动后 800ms 内后台回填让路，先保证当前页跟手。
- **批处理/文库刷新不再重复拉**：沿用已有的 `EVT.libraryChanged` 广播；本轮只补了分组/导入后的刷新，不新增轮询。

### 代码位置
- `src/renderer/src/features/library/LibraryList.tsx`：`authorOf` effect、`forItemsLocal`
- `src/main/ipc/authors.ts`、`src/main/services/authors.ts`：`forItemsLocal`
- `src/renderer/src/App.tsx`：两视图同时挂载、`resetKey`
- `src/renderer/src/features/reader/PdfViewer.tsx`：`lastScrollAtRef`、`backfill`
- `src/renderer/src/styles.css`：`.scrollpage { content-visibility: auto; ... }`

### 验证
- `npm run typecheck`、`npm run test:unit`、`npm run build`、完整 E2E 通过。
- E2E 的“快速翻页/双缓冲/切视图”检查保持通过。

### 边界
本轮没有做“万篇文库”的压测；性能收益来自去掉 N+1 IPC 和避免视图重建，属于结构性修复，不是某个固定毫秒数。

## 2. 翻译后表格消失 / 大小不正常，正文只翻了一部分

### 症状
带表格的页面翻译后，表格下半部分消失或排版错乱；表格外正文只翻译了一部分，甚至正文也被吞掉。

### 根因
旧流程把“表格检测”放在**合段之后**，而且只认“表格内字号明显小于正文”的框：
- 与正文同字号的表格会被并入正文，整表送去翻译；长译文按正文宽度写回，直接把表格压坏。
- 没有竖线的三线表（booktabs）`find_tables()` 默认策略识别不到，单元格又与上下正文合并，擦除/回填后内容消失。
- 合段后表格和正文已经混成一段，再想保护就晚了。

### 方案
- **先检测表格，再合段**：在 `simple_translate` 的段落合段之前生成 `table_rects_by_page`。
- **两类证据**：
  1. 线条聚类：≥2 条横线 + ≥2 条竖线，或 ≥3 条同宽横线，覆盖三线表/无竖线表；
  2. `find_tables()` 网格：`row_count >= 2` 且 `col_count >= 2`，并加“单元格文字通常短”的约束，避免把分栏正文误判成表格。
- **表格区域同时是三道屏障**：
  - 合段屏障：表格内文字不再和上下正文合并；
  - 擦除屏障：不把表格区域纳入 `apply_redactions`；
  - 回写屏障：不把正文译文覆盖到表格上。
- **昂贵检测加闸门**：页面没有像表格的线条/题注就不跑 `find_tables()`；图元极多的“病态页”直接跳过检测，避免一页卡几分钟。
- **表格文字保留原样**：这是当前取舍——优先保证表格完整、可读、不消失；表格单元格暂不送模型翻译。若后续要“表格内也翻译”，需要单独做逐单元格排版/回填，不能复用正文的整段写回。

### 代码位置
- `python/app/translate.py`：`_table_regions`、`table_gate`、`table_rects_by_page`、`_table_overlap`、写回循环中的 `obstacles`
- `python/tests/test_translate.py`：表格保护区/三线表回归

### 验证
- Python 翻译测试全通过（含表格保护、三线表、无竖线场景）。
- 实际带表论文重新翻译后，表格保留，表格外正文正常翻译。

### 边界
表格**内文字**目前不翻译；这是为了避免再次出现“表格被压没”。如果用户要求表格内也中文，需要下一轮专门做单元格级翻译与排版，不应直接把表格塞回正文翻译。

## 3. 输入 DOI / arXiv 链接导入失败

### 症状
在文库“输入 DOI / arXiv / 网页链接”里粘贴 DOI 或 arXiv 链接，点导入没有反应或报错。

### 根因
- 旧 `fetch-pdf.ts` 只走 OpenAlex → Unpaywall；Unpaywall 必须带 email，缺 email 时直接失败；没有 DOI 内容协商、Crossref、出版社 landing page、arXiv 兜底。
- 输入框的 `placeholder` 字符串里带换行，视觉上像多行空框；错误又被吞成一句泛化提示，用户不知道卡在哪一步。
- 批量导入和多链接导入共用旧链路，单条失败会影响整批体验。

### 方案
- **统一解析器**：`normalizeIdentifier` 识别 DOI / arXiv / URL / 裸链接；`resolvePdfUrlDetailed` 按顺序尝试：
  1. DOI content negotiation（`application/pdf`）；
  2. OpenAlex / Unpaywall（email 可用时）；
  3. Crossref 元数据里的 PDF 链接；
  4. 出版社 landing page 的 `citation_pdf_url` / PDF 链接；
  5. arXiv 的 PDF 地址；
  6. 直接 URL 的 `Content-Type` / `%PDF` 头校验。
- **每一步都留痕**：`ResolveStep` 记录尝试结果，失败时 `summarizeResolveFailure` 返回可读原因；单条失败不再让整批静默。
- **输入框改单行**：`placeholder="DOI / arXiv / 网页链接"`，避免多行错觉。
- **批量导入**逐条解析，单条失败不影响其它条目；成功后刷新文库。

### 代码位置
- `src/main/services/fetch-pdf.ts`：`normalizeIdentifier`、`resolvePdfUrlDetailed`、`extractPdfLinks`、`importFromUrl`、`importManyFromUrls`
- `src/renderer/src/features/library/LibraryList.tsx`：URL 输入框、`importFromUrl`
- `src/main/ipc/library.ts`：导入 IPC

### 验证
- 单测覆盖 DOI/arXiv/URL 识别、PDF 头校验、HTML 链接提取、失败摘要。
- 类型检查与完整 E2E 通过。

### 边界
出版社付费墙/Cloudflare 仍然可能拿不到 PDF；此时会给出具体失败原因，而不是假装成功。没有配置 Unpaywall email 时会跳过该源，继续走其它源。

## 4. 文库分组

### 方案
- 数据库 `items` 加 `group_name TEXT`，`migrate.ts` 做幂等加列迁移，旧库不丢数据。

- 主进程：`library.listGroups`（GROUP BY 计数）、`library.setGroup`、`library.setGroupMany`。
- 文库顶部分组下拉：全部 / 未分组 / 各组（带计数）；新建分组后立即切换，之后导入的文献通过“导入前 id 集合 vs 导入后 id 集合”的差集自动归入当前组。

### 代码位置

## 5. 切换页面闪一下 / 卡一下

### 根因
`viewMode` 变化导致阅读器重新挂载；`ErrorBoundary` 的 `resetKey` 包含 `viewMode`，即使文档没变也会重置整棵子树，页码/滚动/位图缓存全部重建。

### 方案
- `App.tsx` 同时挂载两套阅读视图，用 `.reader-stack__pane--hidden { display: none }` 隐藏非当前视图。
- `resetKey` 只保留 `attachmentId + translationId`；同一文档切原文/对照不再重建。
- 非当前视图仍保留 `PdfViewer` 的 `docCache` 与页面位图；切回来直接显示。
- 查找的 `query/tick/status` 只传给当前可见视图，避免隐藏视图的搜索结果覆盖可见视图的计数。
- E2E 的可见性断言改为“只检查可见 pane 的文本层”，避免把隐藏视图的 DOM 当成可见内容。

### 代码位置
- `src/renderer/src/App.tsx`：`reader-stack`、两视图、`resetKey`
- `src/renderer/src/features/reader/CompareView.tsx`、`PdfViewer.tsx`
- `src/renderer/src/styles.css`：隐藏 pane
- `scripts/e2e.cjs`：可见性检查

### 验证
- 完整 E2E 通过；切原文/对照不再触发阅读器重挂载。

### 边界
第一次打开某文档/第一次生成译文仍需要解析，这是不可避免的冷启动；本轮去掉的是“已经打开过还重建”的热切换成本。

## 6. 分不清正文 / 参考文献 / 附录

### 方案
- Python 侧新增 `_page_roles_from_texts`：
  - 首页且像标题/作者/摘要 → `front_matter`；
  - 命中 References/参考文献标题 → `references`；
  - 命中 Appendix/附录/Supplementary 标题 → `appendix`，并且**从 references 状态切回正文**；附录是正文，必须翻译；
  - 其余 → `body`。
- 参考文献页不强制翻译，避免浪费模型；附录页正常翻译并按正文验收。
- QA 结果写 `qa.verification.pageRoles`（1-based 页号 → 角色）；翻译面板显示“页面结构：正文 N · 参考文献 M · 附录 K”。
- 验收/重译按角色分流：`references` 的 stuck 页记为 skipped，不算正文失败；`appendix` 按正文比例验收，只有“已写够比例但公式/证明区域 stuck”才特殊处理。

### 代码位置
- `python/app/translate.py`：`_is_appendix_heading`、`_page_roles_from_texts`、`_verify_one_page`、`qa.verification.pageRoles`
- `src/renderer/src/features/translate/TranslationPanel.tsx`：`roleSummary`
- `python/tests/test_translate.py`

### 验证
- Python 测试覆盖附录标题、参考文献页、首页 front matter。
- 旧译文没有 `pageRoles` 时面板不显示，不报错。

### 边界
页面角色是**规则识别**，不是模型分类；极少数没有标准标题的附录/参考文献可能仍被判成正文。误判只影响“是否跳过/如何验收”，不会删原文。

## 7. 右侧译文滚动时，左侧原文不跟着走

### 症状
原来只有“原文 → 译文”单向联动：拖动右侧译文，左侧原文不动。

### 方案
- `CompareView` 增加 `originRef`：每次联动写入前标记“这次滚动来自哪一侧”，500ms 内另一侧的回声不再反向驱动，避免 A→B→A 循环。
- 右侧 `PdfViewer` 传入受控 `currentPage` 与 `onPageChange`；右侧翻页/滚动时回调 `onRightPage`。
- 右侧滚动锚点回调 `onRightScroll` → 左侧 `syncAnchor`；左侧已有 `applyingScrollRef` 防回声。
- 工具栏“联动”开关关闭时，两侧都不互相驱动。

### 代码位置
- `src/renderer/src/features/reader/CompareView.tsx`：`originRef`、`onLeftScroll`/`onRightScroll`、`onRightPage`
- `src/renderer/src/features/reader/PdfViewer.tsx`：`syncAnchor`、`onScrollAnchor`
- `scripts/e2e.cjs`：新增“右侧滚动 → 左侧同页”断言（右侧目标页用 0-based `data-page`）

### 验证
- E2E 双向联动检查通过（右滚到第 2 页，左也到第 2 页；再反向滚回第 1 页）。
- 单侧联动/关闭联动时不会互相抢滚动。

### 边界
两侧页面高度不同，同步的是“页 + 页内比例”，不是像素级完全对齐；同一源页内会有几像素误差，这是版面差异导致的正常现象。

## 8. 图表浮窗放大 + 清晰度

## 11. 已知边界 / 后续建议

1. **表格内文字暂不翻译**：当前优先保证表格不消失、不变形；若需要单元格中文，需要单独做“单元格翻译 + 单元格排版”，这是下一步而不是本轮补丁。
2. **页面角色是规则识别**：没有标准标题的附录可能误判；误判只影响验收归类，不影响原文。
3. **双向联动是页+比例同步**：左右 PDF 版面高度不同，无法做到像素级完全一致。
4. **导入仍受出版社限制**：付费墙/反爬拿不到 PDF 时会明确失败，不会伪造成功。
5. **性能没有做万篇压测**：本轮去掉的是结构性浪费（N+1 IPC、视图重建、远处回填抢线程），建议后续用 500+ 条目做一次真实计时。
6. **旧译文**：表格保护、页面角色、双向联动中的新字段只对**新翻译**生效；旧译文需要重新翻译才能获得 `pageRoles` 与新排版。
